# Paxos 复制状态机 KV（kvpaxos）

课件：L07《Replication and Consensus》第 51–56 页。

## 算法

- 每台服务器保存一份操作日志；日志的每个槽位（slot）是一个**独立的** Basic Paxos 实例，有自己的提案号 `round.node`、承诺和投票。
- 客户端可以把 `Put(key, value)` / `Get(key)` 发给任意服务器。服务器把操作提议到**自己还不知道已决定的最低槽位**：
  - 该槽位最终选定的是自己的操作：完成；
  - 选定的是别人的操作（Prepare 带回了已接受的值，或收到 Decide）：执行它，`conflicts` 加一，到下一个槽位重新提议。
- 每个槽位内部与 `paxos-basic` 相同：`Paxos.Prepare{slot, n}` → 多数派承诺，采用最高 `acceptedN` 的值 → `Paxos.Accept{slot, n, op}` → 多数派接受即选定 → 广播 `Paxos.Decide{slot, op}`。
  被拒绝或 1.5 秒内没有多数派时，随机退避后用更高编号重试；整个操作 6 秒内没有完成就返回错误。
- 已决定的槽位**严格按顺序**执行（遇到空洞就停下），所以所有副本以相同顺序执行相同操作。
  `Get` 也写入日志，它的结果是执行到它那个槽位时的值（课件 p.55「Scan up to LogEntry 4」）。
- 操作在消息里是一个字符串，如 `put a=1 @2.5`：`@2.5` 是 node-2 的第 5 个操作，用来判断赢得槽位的是否是自己的操作。
- 持久化：每次 acceptor 回复前，用 `sdk.Save` 保存各槽位的承诺/投票和已决定的日志；存储不保存，重启时由日志重放得到。
- 追赶：服务器收到某槽位的 Prepare/Accept/Decide 时，若发现更低的槽位有空洞（例如它曾崩溃），1 秒后对每个空洞**并发**运行一次 Paxos，提议 no-op。
  如果该槽位已选定，Prepare 一定会从多数派中看到那个值，于是重新选定的仍是原来的操作。

## 节点状态

| 字段 | 含义 |
| --- | --- |
| `role` | 总是 `replica`（没有 leader，所有服务器对等） |
| `log` | 已决定的日志，`槽位:操作`，`?` 表示还不知道的空洞 |
| `appliedIndex` | 已按顺序执行到的槽位 |
| `store` | 执行日志得到的键值存储 |
| `lastResult` | 本服务器最近一次客户端操作的结果，如 `get a = 3 (slot 4)` |
| `conflicts` | 提议的槽位被别人的操作赢走的次数 |
| `proposingSlot` | 正在为客户端操作提议的槽位 |
| `catchingUp` | 正在追赶（no-op 提议）的空洞数 |
| `recovered` | 本进程是否从持久化文件恢复 |

## 应用输入

| 方法 | 作用 |
| --- | --- |
| `Application.Put(key, value)` | 写入；返回占用的槽位。拿不到多数派时 6 秒后返回错误 |
| `Application.Get(key)` | 读取；读操作也进入日志，返回槽位和读到的值 |

## 观察场景

`node scripts/scenarios.mjs run paxos-kv <场景ID>` 自动回放，然后在「运行历史」中逐步查看。

### sequential · 不同服务器依次写入与读取（p.54–55，5 节点）

1. `Put(a,1)`@node-1、`Put(b,2)`@node-3、`Put(a,3)`@node-5、`Get(a)`@node-2。
2. 每个操作占一个槽位，所有服务器的日志都是 `1:put a=1, 2:put b=2, 3:put a=3, 4:get a`；Get 返回 3。

思考：Get 为什么也要进日志？直接读 node-2 的本地存储会有什么问题？

### concurrent · 两个写入竞争同一槽位（5 节点，延迟 300ms）

1. node-1 `Put(x,紫荆)` 与 node-2 `Put(x,澜园)` 同时发出，都提议槽位 1。
2. 槽位 1 只能选定一个；输的一方在 Prepare 中看到对方已接受的值，帮它完成槽位 1，然后在槽位 2 提议自己的操作（`conflicts=1`）。
3. 所有服务器日志相同，x 的最终值由槽位顺序决定、处处一致。

### crash-catchup · 少数节点崩溃与恢复追赶（p.56）

1. node-5 参与了槽位 1 后崩溃；其余 4 台继续提交槽位 2–4（多数派仍在）。
2. node-5 恢复：从持久化文件读回槽位 1，`appliedIndex=1`。
3. 下一个写入（槽位 5）的 Prepare 到达 node-5，它发现空洞 2–4，对它们并发提议 no-op，Prepare 带回已选定的操作；node-5 的日志与存储追上其他服务器，不含任何 no-op。

思考：如果 acceptor 不持久化承诺和投票，崩溃恢复还安全吗？（参见 `paxos-basic` 的 amnesia 场景。）

### partition · 少数派分区无法提交（CAP 中的 CP）

1. 把 {node-4, node-5} 与 {node-1, node-2, node-3} 隔开。
2. node-4 的 `Put` 拿不到多数派承诺，6 秒后报错；node-1 的 `Put` 正常提交。
3. 分区恢复后再写一次，少数派追上同一日志；失败的写入从未出现在日志中。

## 实现边界

- 没有固定 leader（Multi-Paxos 优化），每个槽位都跑完整的两阶段；并发写入时会有冲突和重试。
- 每台服务器同一时刻只处理一个客户端操作（其他请求排队）。
- 客户端超时不代表操作一定没有执行：若 Accept 已被多数派接受但回复丢失，操作之后仍可能出现在日志中；这里没有做客户端去重。
- 追赶只在看到更高槽位的消息时触发；没有新流量时，错过最后一个 Decide 的服务器要等下一次操作才会补上。
- 日志不截断、不做快照；成员变更（p.57–58）不实现。
