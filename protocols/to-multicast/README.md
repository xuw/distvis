# 全序多播：复制银行账户

课件：L06《Distributed Synchronization (2)》第 2–7 页。

## 算法

课件第 3 页的例子：账户在每个节点上各有一个副本，初始余额 1000。北京存入 100，上海同时计息 1%；若各副本按收到顺序执行，会出现 1000+100→1111 与 1000×1.01+100→1110 两种结果。

`ordered` 模式（全序多播）：

1. 发送方时钟加一，用 Lamport 时间戳 `L.id` 标记更新；
2. 多播给所有节点，包括自己（发给自己不走网络）；
3. 收到更新：放入按 `(L, 发送者编号)` 排序的优先队列，并向所有节点多播 ACK（ACK 的时间戳大于更新的时间戳）；
4. 只有当更新位于队首、且收到了全部 N 个进程的 ACK（含自己）时才交付，即应用到余额上。

课件假设的 FIFO 信道与不丢消息用以下方式满足：每个对端一个发送 goroutine + 队列，按序停等发送（上一条返回后再发下一条）；调用失败（节点崩溃、超时 8 秒）就每秒重试队首消息，直到对方应答。

`naive` 模式：收到更新立即执行，不发 ACK。

一次多播的消息数：N-1 条 `TOM.Update` + N(N-1) 条 `TOM.Ack`（每个接收者都向其余 N-1 个节点发 ACK），即 O(N²)。

## 节点状态

| 字段 | 含义 |
| --- | --- |
| `role` | `waiting` 队列非空 / `replica` 空闲 |
| `mode` | `ordered` 或 `naive` |
| `clock` | Lamport 时钟 |
| `balance` | 本副本的余额 |
| `queue` | 优先队列，每项 `L.id 操作 acks=k/N`；操作为 `?` 表示 ACK 先于更新本身到达 |
| `delivered` | 最近 10 个已交付的更新，按交付顺序，如 `1.1 +100`、`1.3 +1%` |
| `deliveredCount` | 已交付总数 |
| `updatesSent` / `acksSent` / `messagesSent` | 本节点发出的更新、ACK 及其总和（不含重试） |

## 应用输入

| 方法 | 作用 |
| --- | --- |
| `Application.Deposit(amount)` | 多播一次存款 |
| `Application.Interest(percent)` | 多播一次计息（整数百分比，结果按分四舍五入） |
| `Application.Mode(mode)` | 切换本节点的交付方式并把本副本重置为 1000（时钟保留）。只作用于本节点，实验前应对每个节点都设置；混用两种模式时 ordered 节点会一直等不到 naive 节点的 ACK |

## 观察场景

用 `node scripts/scenarios.mjs run to-multicast <场景ID>` 自动回放后，在「运行历史」中逐步查看。

### naive-diverge · 副本分歧（3 节点，延迟 800ms）

1. 三个节点都切到 `naive`；把 node-1→node-2 设为 100ms，node-3→node-2 设为 2500ms。
2. node-1 `Deposit(100)`，node-3 同时 `Interest(1)`。
3. node-1、node-2 先存款后计息 = 1111；node-3 先计息后存款 = 1110。

### ordered-agree · 全序交付（同样的链路）

1. 同样的并发更新，时间戳分别为 `1.1` 和 `1.3`。
2. 1.5 秒时 node-3 自己的计息 `1.3 +1%` 还在队列中等待 ACK，余额仍是 1000。
3. 所有副本都按 `1.1 +100`、`1.3 +1%` 交付，余额都是 1111。

观察：由于停等发送，node-3→node-2 这条慢链路上的更新和两条 ACK 是串行的，全部交付要约 10 秒。

思考：node-2 先收到 1.1 并且早已收到 node-1 的 ACK，为什么还不能交付 1.1？（它必须收到 node-3 的 ACK，才知道 node-3 不会再发出时间戳更小的更新。）

### message-cost · N=4 的消息开销

node-1 存款一次：3 条 `TOM.Update`、12 条 `TOM.Ack`；node-2 再计息一次后累计 6 与 24。

思考：Lamport 互斥为什么只把回复单播给请求者？

### crash-blocks · 一个节点崩溃，全体停止交付（3 节点）

1. 崩溃 node-3，node-1 存款。
2. node-1、node-2 的队列都停在 `1.1 +100 acks=2/3`，余额 1000：交付需要所有进程的 ACK。
3. 恢复 node-3：node-1 重试的更新到达 node-3，node-3 入队并多播 ACK，node-2 重试的 ACK 也到达；三个副本都交付，余额 1100。

思考：能否在超时后把 node-3 当作「已同意」？如果 node-3 其实只是很慢，会发生什么？

### crash-persist · 崩溃恢复后靠持久化的队列继续（3 节点）

1. 崩溃 node-2，node-1 存款：node-1、node-3 的队列停在 `1.1 +100 acks=2/3`（缺 node-2）。
2. 再崩溃 node-3：它发往 node-2 的 ACK 还在发送队列里，随崩溃丢失；但队列本身已持久化。
3. 恢复 node-2：收到重试的更新并多播 ACK，node-1 集齐 ACK 先交付；node-2 还缺 node-3 的 ACK。
4. 恢复 node-3：从持久化的队列补发 ACK，node-2、node-3 也交付，三个副本都是 1100。

思考：如果 node-3 的队列不持久化，恢复后会怎样？（node-1 发给它的更新早已送达、不会再重发，node-2 永远等不到 node-3 的 ACK。）

## 实现边界

- 副本状态（模式、时钟、余额、队列、已交付记录）每次变化后用 `sdk.Save` 持久化，崩溃恢复后继续；恢复时对队列中的每个更新重发 ACK，并重发自己发起的更新（接收方按时间戳去重）。发送队列本身不持久化，因此需要这种补发。
- 所以恢复后交付会继续；如果不持久化，恢复的节点会从 1000 重新开始并错过崩溃前已交付的更新，副本就不再一致。
- 不处理成员变更，也不容忍永久故障：一个节点不恢复，整个系统永远阻塞（课件第 48 页：这些算法都不能容忍进程故障）。
- `Mode` 是本地设置，不做全局协调；运行中途切换模式可能让在途消息与新状态混在一起。
